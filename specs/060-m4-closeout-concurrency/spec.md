## Bounded claim contract

1. Resolve the worker timeout from one validated operational source: default 30, strict integer **1..120 seconds**. Reject null, booleans, floats, malformed strings and out-of-range values; environment decimal integer text may be deliberately parsed to an integer, but may not be blindly cast so malformed input becomes valid. Derive lock wait solely as timeout + 5. Remove the unused independent `clip_analysis_lock_wait_seconds` key/environment lookup from active implementation/configuration, not history. `lock_wait_seconds` remains required execution metadata, not an independent setting.
2. Validate before timeout arithmetic, SQL setting construction, contended clip writes/claims, or process creation. Invalid operational configuration produces a fixed sanitized `invalid_configuration` failure to the caller/queue, invokes no clip worker, and makes no unsafe clip/asset mutation. Do not attempt an unbounded failure-finalization claim with invalid configuration. Completed reuse needs no new attempt or operational metadata rewrite. Valid configured claims for controlled input/worker failures still follow the ordinary atomic failed-attempt policy.
3. Inside the clip transaction, apply PostgreSQL's transaction-local `lock_timeout` to the derived bound **before any potentially contended claim statement**, including insert/unique-conflict waits, foreign-key waits, and row locks. Use verified PostgreSQL syntax (for example its transaction-local configuration function with safely bound text); do not assume parameter placeholders work in `SET LOCAL` grammar. Never change global/session defaults in production. Same-connection settings restore after commit and rollback; independent connections are unaffected.
4. Safely establish/claim one row using the existing DB unique constraint, conflict-safe insert and fresh locked reread. Prefer `ON CONFLICT (media_asset_id) DO NOTHING` plus `SELECT ... FOR UPDATE`; lock/reread even when pre-read state existed. Do not use app-only mutexes, sequential firstOrCreate assumptions, or unhandled unique exceptions. Both initial callers may observe no row; only the owner executes analysis. A loser waits within the bound, then rereads and reuses completed data without worker execution.
5. A conflict can be followed by an empty reread if deletion won. Treat a missing asset or missing locked row as internal **deleted/no-op**: no worker, no recreation, no claim of clip resolution or asset completion. FK/unique/lock errors abort PostgreSQL transactions: roll back the failed transaction (or a correctly scoped savepoint) before any recovery query. Never catch a PostgreSQL error and reread in an aborted transaction. Recheck deletion on a usable connection; no raw DB exception escapes.
6. Freshly select authoritative readiness/inputs under the claim. Keep transitions, worker execution, validation and terminal snapshot writes in the same clip-only transaction. Expected malformed output/process failures commit a sanitized failed attempt with no partial result. Unexpected aborts/connection loss roll back, preserving prior durable pending/failed state (or absence for a new row), and remain retryable rather than falsely resolved.
7. Contention timeout (real SQLSTATE 55P03) yields internal **busy** after rollback, no worker and no owning analysis/asset mutation or success/finalization. Diagnostic reporting uses a fixed category, not a persisted failure on the owner's row. At the void job boundary busy means return without finalizing; deleted means safe return; completed reuse means use the existing persisted result. Internal representations may follow existing conventions but these meanings are mandatory.
8. Process timeout, applied lock wait, and persisted `execution_parameters.timeout_seconds/lock_wait_seconds` must describe the same actual attempt. Completion validation requires strict types/range and `lock_wait_seconds === timeout_seconds + 5`, not comparison to a removed setting or a later ambient config. Preserve independent result validation. Capture settings once per attempt; do not silently recalculate inconsistently across job/action/model.
9. Probe, scene detection, extraction and transcription run **outside** the clip transaction and its row lock. Only a bounded metadata computation holds it. No new long-lived lock around the media pipeline.

## Authoritative exception boundary — independent clarification

Historical #58 requires both expected worker/validation failures to commit (Lifecycle step 3) and unhandled exception/crash rollback (step 5). Its CLI runtime-error envelope is a classified worker result, not permission to convert every PHP throwable into a resolved analysis. #60 preserves that distinction:

- Expected clip-stage failures include actual process timeout, nonzero exit, malformed worker JSON, invalid contract/input/result and explicit controlled upstream classifications. They may commit a fixed sanitized failed attempt inside the claim, with no partial result/input snapshot. Invalid operational configuration retains the pre-claim rule above. Catch at the boundary that establishes the classification, not by arbitrary exception message or a blanket `Throwable` conversion.
- Unexpected application/programming/caller/infrastructure throwables (including missing Mockery interactions, unexpected RuntimeException/Error, and DB errors) must escape the claim closure so PostgreSQL rolls back. This applies during action/process construction/execution, validation, persistence and finalization. A DB error is not a worker error. Known lock timeout and confirmed deletion retain their separate post-rollback busy/deleted outcomes. Other DB/runtime aborts are unresolved and retryable.
- After rollback, the outer job must signal a **sanitized retryable exception** to its caller/queue, not silently return normally. Use fixed `clip_analysis_aborted`, empty stderr and no original/previous throwable, raw message, SQL, bindings or payload. A narrowly distinguished fixed abort marker using the existing exception class is sufficient; it must be rethrown through inner expected-failure catches, never converted to `analysis_failed`. The action boundary must likewise not turn unexpected throwables into ordinary worker failure. Direct action callers receive a sanitized abort, not raw exceptions. No global exception-handler change is authorized.
- A failed transaction commits neither analyzing nor partial JSON; pending/failed raw snapshots survive exactly and a new row remains absent. Compensating deletion of an already committed placeholder is not transaction rollback and does not prove crash safety. Keep creation within the bounded claim as already required above.
- Queue delivery of an abort must retry under the bounded existing policy. Only **actual exhaustion**, in a separate safe serialized finalization claim, may resolve an unclaimed pending/failed analysis through analyzing to sanitized failed and fail a nonterminal asset. Use fixed `clip_analysis_aborted` for this cause; do not mislabel it `upstream_not_ready`. Completed/locked analysis, deleted assets and terminal assets must not be overwritten. This does not change the three-attempt/5-second upstream-not-ready policy or upstream scene/audio/transcript behavior.

The six reported scene-test failures are incomplete valid-ready clip fixtures, not evidence that scene orchestration should skip clip analysis. Their per-test decisions and the additional ready contexts exposed by proper exception propagation are in `plan.md`. No generic/global mock or suppression of unexpected aborts is permitted.

### Process-exception dataset clarification

The existing `ClipAnalysisResultTest.php` sanitization dataset named `process exception` injects a plain PHP `RuntimeException('PRIVATE_SENTINEL')` from a fake process `run()`. It supplies no timeout, exit failure or classified worker error. This is an **unexpected runtime abort**, requiring exactly `clip_analysis_aborted`, not ordinary `Clip analysis failed`. Its location in a process double does not classify its cause. Preserve the injected throwable and all privacy assertions; correct the case name and explicit expected category only. The other four malformed-output datasets remain ordinary sanitized clip failures. No blanket catch of PHP or Symfony RuntimeException is authorized; specific recognized timeout/nonzero-exit/validation controls remain expected failures. This clarification requires no production correction for this dataset and does not relax atomic first creation or real termination/rollback requirements.

### Eligible-empty persistence clarification

The unconditional `Candidates must not be empty` guard in `ClipAnalysisValidator::validateCompletion` is a defect against approved #58, not a reason to change the scene fixtures to FAILED. #58 explicitly permits executed empty-scene/all-ineligible results and requires the same invariants at action and model completion boundaries. Preserve COMPLETED with `candidates=[]`, null error and full provenance **only when** independently validated snapshot inputs/configuration rederive zero selected candidates. Required fields must remain present; missing/null/object candidates are not an empty-list default. Invalid duration, scene/transcript timing, configuration, algorithm/version, provenance or execution metadata must still reject before any model update, even when zero candidates are expected. An eligible nonempty set can never be replaced by an empty response. No early empty-success shortcut, synthetic result, scene/duration/configuration change or scoring/ranking change is authorized.

## Required concurrency and recovery scenarios

These are the issue's nine acceptance scenarios (not the differently numbered historical #58 table). Dedicated real PostgreSQL tests must exercise production paths, independent processes/connections, committed fixtures, explicit barriers and bounded teardown. No SQLite substitution, skipped cases, sleep-only scheduling, or broad-total inference.

| ID | Scenario | Observable outcome |
|---|---|---|
| C1 | First-create race: both processes observe absence before insert | Real unique-conflict arbitration, exactly one durable row and **one total worker call**, loser safely rereads/reuses identical completed snapshot; later completed reuse unchanged. |
| C2 | Concurrent failed retries | Same row claimed serially, stale error cleared by owner, no overlapping workers, first successful retry terminal, second reuses without worker call. |
| C3 | PostgreSQL-enforced contention timeout | Real bounded lock wait, sanitized busy; no owner/asset mutation or success claim by contender; owner can complete. Cover existing-row and initial insert-conflict waits. |
| C4 | Unexpected exception/abort and real connection termination | No committed analyzing/partial result/input snapshot; preseeded pending and failed cases survive exactly, new-row rollback leaves absence; subsequent queue retry can claim and complete. |
| C5 | Real queue bounded attempts/exhaustion (`upstream_not_ready`) | Three attempts, 5-second retry delay, no worker/premature completion while upstream active; exhaustion atomically resolves unclaimed analysis through legal analyzing-to-failed transition with fixed `upstream_not_ready`. Nonterminal asset becomes failed; already completed/failed assets stay terminal unchanged; locked/completed analysis not overwritten. Include exhaustion after rollback. |
| C6 | Stale caller/late failure callback | Actual finalization callback cannot overwrite completed snapshot **or downgrade completed asset**; terminal error/timestamps remain unchanged; stale clip evaluation reuses result. |
| C7 | Deletion race | FK cascade authoritative; deletion while claim active serializes safely; eventual asset/analysis absence, no orphan/recreation/late successful write. Also cover delete winning before claim and empty reread. |
| C8 | Lock scope | Each upstream stage executes with no clip transaction/row lock; independent observer can acquire clip row during upstream work; clip worker executes inside exclusive claim. |
| C9 | Local-setting isolation | Effective derived setting during claim; prior setting restored after **commit and rollback**, later transaction unchanged, independent live connection unaffected. |

Retain and execute original malformed output/error/nonzero-exit and worker-timeout cases in addition to C1–C9. They must commit atomic sanitized failed results, preserve upstream scenes/transcripts, allow serial retry, and terminate timed-out child processes. Ordinary resolved clip failure permits normal asset completion only when scene/audio paths are also resolved; extraction failure keeps the asset failed. Not-ready/busy/aborted/deleted outcomes cannot masquerade as resolved success.
